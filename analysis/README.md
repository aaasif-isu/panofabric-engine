# Rebase + Ledger Experimental Analysis

This repository contains the data extraction, statistical analysis, and figures for the **Rebase + Ledger** ablation experiments, evaluating its effectiveness at resolving slow-worker starvation in asynchronous Decoupled HeLoCo and Decoupled DiLoCo.

## Data Provenance and Path Wiring
This entire analysis is strictly pinned to the verified artifacts generated by the experimental pipeline. The script `analysis/scripts/run_analysis.py` fails-fast if paths, checkpoints, or configuration variables are missing or mismatched.

### Input Directories
*   **Original:** `outputs/method_comparison/20261013T094124-9a2f23`
*   **Rebase+Ledger:** `outputs/method_comparison/20261013T094907-7cfedb`

### Configuration and Checkpoint Verification
Before computing statistics, the script verifies:
1.  **Configuration Verification:** Reads `experiment.yaml` from both methods in both directories, ensuring `rebase: False, ledger: False` in the original directory and `rebase: True, ledger: True` in the new directory. It also confirms that critical experimental control variables (e.g., `num_fragments`, `min_quorum`, `min_local_steps`, `scheduler`) are perfectly identical across both runs.
2.  **Initial Checkpoint Verification:** Reads `comparison.json` in both directories to assert that the `initial_parameters_sha256` keys are an exact match, proving both runs initiated from the identical mathematical starting point.

## Reproduction
To regenerate the figures and CSV data from the raw outputs, you can run the pipeline from *any working directory* inside the repository:
```bash
python analysis/scripts/run_analysis.py
```

## Key Findings

### 1. Starvation Resolution & Participation Fairness
The Rebase + Ledger mechanism successfully eliminated slow-worker starvation.
*   **Original runs:** The slow workers (Learner 1 [French] and Learner 2 [German]) were continuously overwritten by fast workers before completing `min_local_steps`. Learner 2 contributed to **0 out of 100** aggregations.
*   **Rebase + Ledger:** The ledger safely preserved their progress across revisions. Learner 2 successfully contributed to **56 out of 100** aggregations, and Learner 1 contributed to **76**.
*   **Fairness:** Jain's Fairness Index for accepted contribution counts skyrocketed from **0.50 (highly monopolized) to 0.95 (highly equitable)**.

### 2. Global and Per-Language Convergence
Allowing delayed, rebased gradients to enter the global model proved highly constructive rather than acting as stale noise.
*   **Global Loss:** Decoupled HeLoCo overall validation loss dropped notably from **3.053 to 2.982**.
*   **Language Improvements:** The German and French validation losses dropped by **~0.21 and ~0.14 points** respectively, directly reflecting their newfound participation in the model trajectory.

### 3. System Efficiency and Overhead
*   **Throughput:** By preserving local steps rather than discarding them, the globally accumulated `total_tokens` processed increased by **14%** (1.18M -> 1.35M), raising the global tokens/sec throughput.
*   **Quorum Sizes:** The number of concurrent learners merged per server update shifted drastically. In the original run, 99% of commits were minimum quorums (2 learners). With Rebase+Ledger, **56% of commits successfully aggregated all 4 learners**.
*   **Communication Overhead:** RX traffic (Learners -> Server) increased from **~3.05 GB to ~4.56 GB**. This is expected: starved workers are now actively transmitting accepted snapshots over the wire rather than being continually pre-empted locally.

### 4. Weaknesses & Regressions
*   **Dilution of Fast Workers:** The Spanish worker (a fast node) exhibited a minor validation loss regression (e.g., 2.803 -> 2.847). This is an expected trade-off when diluting a fast worker's monopoly with updates from a diverse multilingual quorum.
*   **Compute Overhead:** Wall-clock time increased marginally (~10%, 44.8s -> 49.3s) due to the CPU overhead of receiving and merging 4-learner quorums compared to 2-learner quorums.

## Limitations
*   **Convergence vs. Time:** Intermediate evaluation datasets were unavailable. The experiment only recorded initial and final cross-entropy evaluations, preventing the plotting of continuous validation loss against elapsed time.

## Recommended Future Analyses
Based on the patterns observed in this data, the following 3 analyses are highly recommended to further investigate the mathematical and networking implications of Rebase + Ledger:

1.  **Staleness Attenuation vs. Assigned Weight:** Plot the assigned aggregation weight (from `weights_list`) against the physical `elapsed_s` time-gap of the snapshot. This will mathematically reveal whether the `tokens_squared_per_step` merging logic aggressively attenuates heavily delayed Rebased updates to prevent instability.
2.  **Pseudo-Gradient Cosine Similarity:** Extract the accepted Rebased pseudo-gradients for the slow workers and compute their cosine similarity against the fast workers' concurrent updates. This proves whether Rebase algebraically aligns with the current trajectory or simply injects orthogonal momentum.
3.  **Transient TCP Congestion:** Correlate `bandwidth_timeseries.csv` against periods of maximum quorum size (4 workers). This will reveal if allowing slow workers to eventually upload snapshots causes transient network bursts that inadvertently penalize the fast workers' upload latency.
